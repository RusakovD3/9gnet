# Математика, атаки и решения GNet9 — простое объяснение

Этот документ отвечает на четыре вопроса, которые были важны в переписке
Попкова с DeepSeek: как атака попадает в тензор состояния, что именно показывает
расстояние Хаусдорфа, как на него реагирует критерий Ляпунова и что реально умеет
прогноз Купмана. Он описывает фактический код проекта, а не желаемую будущую
модель.

## Главное в двух абзацах

GNet9 — безопасная исследовательская модель сети. Она строит граф сети и
эталонное состояние `t0`, затем на каждом шаге создаёт отдельный снимок
наблюдаемой телеметрии. Реальных пакетов, команд маршрутизаторам, подбора паролей
или изменения внешней сети программа не выполняет.

В модели есть три разные математические задачи.

1. **Хаусдорф состояния** отвечает на вопрос: «насколько набор измеренных
   состояний сети отличается от `t0`?» Больше — хуже, но это не физическое
   расстояние между иконками на рисунке.
2. **Купман/DMD** описывает нормальную динамику около `t0` и замечает отклонения
   только по уже полученной телеметрии.
3. **Ляпунов** измеряет, растёт или затухает энергия этого отклонения для
   используемого линейного оператора. Положительный рост усиливает сигнал
   арбитру, но сам по себе не доказывает устойчивость реальной сети.

## Что взято из обсуждения Попкова и DeepSeek

| Уточнение автора | Решение в GNet9 |
|---|---|
| Атаку нужно явно сопоставить с тензором. | Есть таблица «MITRE-техника → уровни → метрики тензора → наблюдения → защита», экспортируемая в `mitre_attack_catalog.json`. |
| Нельзя говорить, что Купман знает все атаки MITRE. | Оператор учится только нормальному режиму `t0`. Поддержаны лишь явно перечисленные сценарии; неизвестное событие может дать аномалию, но не гарантированное распознавание типа. |
| Нужно показать, как меняется Хаусдорф. | Ниже приведены точки, формула, пример и поля JSON, по которым виден вклад конкретного объекта. |
| Нужно объяснить реакцию Ляпунова. | Ниже описан расчёт `P`, энергии `V`, её изменения и порог, после которого возникает план защиты. |
| Термины не должны обещать больше, чем делает код. | Близость угрозы к Gold-узлу названа близостью по задержке, а не Хаусдорфом. `risk_score` — балл риска, а не вероятность. |

## Как один шаг проходит через модель

```text
Граф и t0
   ↓
Потоки и безопасная телеметрия шага
   ↓
Разреженный снимок тензоров L0…L8 и EDGE
   ├─→ Хаусдорф состояния относительно t0
   └─→ Арбитратор L7: агрегированный вектор состояния
                         ↓
               Купман/DMD и Ляпунов
                         ↓
           план защиты на следующий шаг
                         ↓
Gold-first remapping только во временном overlay потоков
```

Исходный граф и тензоры `t0` не перезаписываются. Поэтому любой снимок можно
сравнить с одной и той же исходной точкой.

## Что такое тензор в этом проекте

Слово «тензор» здесь не скрывает неопределённую математическую сущность. Каждый
узел или связь, для которых показатель имеет смысл, хранит небольшой именованный
числовой вектор `StateTensor`: например, `cpu_load_percent`, `sla_margin`,
`utilization`, `loss_probability` или `energy_reserve_ratio`.

Для анализа все такие записи можно представить как разреженный пятиосевой набор:

```text
S[объект, уровень, связь, метрика, время]
```

Плотный пятимерный массив не создаётся. Хранятся только существующие записи и
снимки, поэтому в памяти нет миллионов пустых ячеек.

Примеры объектов, которые могут участвовать в сравнении состояния:

| Объект | Что может измениться |
|---|---|
| Абонент L1 `M1_01` | запас SLA, очередь, частота неудачных аутентификаций |
| Маршрутизатор ядра L2 `C1` | загрузка CPU, устойчивость, состояние критической защиты |
| Связь `C1—A1` | загрузка, задержка, вероятность потерь, запас устойчивости |
| Сервер L0 | здоровье сервиса, CPU, RAM, число сессий |
| Питание L6 | запас энергии и доступность питания |

Координаты рисунка сети тоже являются отдельными метриками, когда нужны для
структурного описания, но обычная атака **не передвигает устройство по карте**.
Она меняет телеметрию нагрузки, потерь, очередей, питания или аутентификации.

## Хаусдорф состояния: что именно считается

### Шаг 1. Нормированное изменение каждого показателя

Для метрики `k` объекта `i` строится отклонение от эталона:

```text
z[i, k] = (x[i, k, t] − x[i, k, t0]) / s[k]
```

`s[k]` — масштаб этой метрики: величина в `t0` или естественная единица. Поэтому
проценты, доли, миллисекунды и мегабиты не складываются напрямую без нормировки.

### Шаг 2. Расстояние между двумя записями состояния

Каждая запись имеет постоянную метку: например, «тензор узла `C1`» или «тензор
связи `C1—A1`». Расстояние задаётся так:

```text
d((id, z), (id', z')) = ||z − z'||₂ + 10 · 1[id ≠ id']
```

Первая часть — обычная евклидова норма `||…||₂`, вычисляемая NumPy. Вторая часть
равна 10, если метки различаются. Она не позволяет «подменить» перегруженный `C1`
похожим по цифрам `C2`.

### Шаг 3. Симметричное расстояние Хаусдорфа

Для множества записей в `t0` (`A`) и текущего снимка (`B`) программа считает:

```text
H(A, B) = max( sup[a∈A] inf[b∈B] d(a,b),
               sup[b∈B] inf[a∈A] d(a,b) )
```

Простыми словами: для каждой записи ищется ближайшая запись с другой стороны;
берётся худший из этих ближайших случаев. Считаются оба направления, поэтому
метрика замечает и исчезновение объекта из текущего снимка, и появление нового.

### Как интерпретировать результат

| Поле в `network_dynamics.json` | Значение |
|---|---|
| `distance` | Сырое `H`. В `t0` равно 0; больший результат означает большее расхождение с `t0`. |
| `normalized_distance` | `distance`, ограниченное диапазоном 0…1 для графиков и L7. После 1 сырое значение всё ещё сохраняется в `distance`. |
| `coordinate_hausdorff_distance` | Та же идея, но только для координатных метрик. Не является расстоянием реальных устройств на местности. |
| `top_current_contributors` | До восьми записей, сильнее всего отклонившихся от `t0`, с тремя главными метриками каждой. |
| `structural_difference` | Список исчезнувших и добавленных тензорных записей. |
| `witnesses` | Метки записей, на которых достигнут худший случай в каждом направлении. |

Порог `1.0` — порог заметного состояния для отображения. Нормированное расстояние
до `0.25` видно оператору, но **само по себе не просит ремаппинг**. После `0.25`
его вклад в давление L7 растёт по формуле `(d − 0.25) / 0.75` и ограничивается
единицей. План защиты всё равно требует общего давления больше `0.20` и
подтверждённого события или причинного раннего предупреждения.

### Пример без «разъезжающихся узлов»

В `t0` у `C1` загрузка CPU равна 20%, у связи `C1—A1` загрузка 10%, а у `M1_01`
запас SLA равен 0.80. При DoS меняются CPU `C1`, загрузка и потери связи, затем
снижается SLA абонента. Их нормированные координаты удаляются от нуля, поэтому
растёт `H`. Имена объектов при этом те же: `C1` не стал `C2`, а `M1_01` не
переместился физически. Если тензор `C1` вообще исчезнет из снимка, сработает
штраф за несовпадение метки и `structural_difference` покажет это явно.

### Как расчёт не раздувает память

При неизменном наборе меток одноимённая запись заведомо ближе любой записи с
штрафом 10, пока её отклонение меньше 10. Тогда точный ответ находится без
матрицы всех пар. При новом/удалённом тензоре или очень большом отклонении код
переходит к точному блочному сравнению. Эталон `t0` готовится один раз на прогон.

## Атаки: когда они работают и что меняют

Все атаки живут только в объектах Python. Они создают телеметрию и временный
overlay потоков, но не создают сокеты, не посылают пакеты и не меняют реальное
оборудование.

| Режим `--attack-scenario` | Что происходит |
|---|---|
| `none` | Только здоровая динамика. Атак нет. |
| `mitre-demo` | Одна короткая фиксированная безопасная серия. Удобна, чтобы увидеть каждый поддержанный тип атаки. По умолчанию шаг равен 5 секундам. |
| `predictive-demo` | Воспроизводимая серия по seed: есть наблюдаемые предвестники, прогноз и временное переназначение. По умолчанию 60 шагов по 2 секунды. Окно не может быть короче `max(2, ceil(20 / step_seconds)) + 5` шагов: первая часть нужна для причинных предвестников, оставшиеся пять — чтобы поместилась атака. Brute force в этот учебный генератор не входит. |

Стандартный `mitre-demo` занимает 10 шагов по 5 секунд.

| Шаги | Техника и цель | Что меняется в модели |
|---|---|---|
| 2–3 | T1498.001 Direct Network Flood, `C1` | Нагрузка маршрутизатора и связей, потери, запас SLA. |
| 4–7 | T1110.001 Password Guessing, учётная запись `M1_01` | Только события аутентификации и давление блокировки учётной записи. Нет сетевого flood и потерь легитимного трафика. |
| 5–6 | T1498.002 Reflection Amplification, `SRV_MEDIA` | Нагрузка входа/сервера и защитные меры upstream. |
| 8–9 | T1499.001 OS Exhaustion Flood, `M1_01` | Рост SYN backlog, защита endpoint и карантин подтверждённого источника. |
| 10 | T0831 и T1529, `A3` и `SRV_RTC` | Аномалия питания, UPS ride-through или failover сервера в зависимости от сценария. |

### Медленный brute force T1110.001

Атака `BRUTE_FORCE_GOLD_ACCOUNT` добавлена. Для её численной скорости используется
официальный пример процедуры на странице
[MITRE ATT&CK T1110.001](https://attack.mitre.org/techniques/T1110/001/): в
brute-force режиме APT28 обычно посылала **свыше 300 попыток в час на целевую
учётную запись**. GNet9 берёт ровно 300/ч как документированную нижнюю границу:

```text
300 / 3600 = 0.083333… попытки в секунду
```

То есть ожидается одна неудачная попытка за 12 секунд. Это не универсальный
норматив MITRE и не оценка конкретного оператора. Происхождение видно в
`technical.authentication_attempt_rate_origin` и ссылке рядом с ним в экспортном
каталоге. Остальные численные скорости flood-сценариев помечены
`scenario_assumption`, потому что ATT&CK для них нормативных скоростей не даёт.

Brute force намеренно не создаёт пакеты и не может сам «сломать интернет» в
модели. Он увеличивает `authentication_failure_rate_per_second`, счётчик неудач
и `account_lockout_pressure`. Это соответствует наблюдаемой стороне T1110.001:
серии неудачных входов и возможные блокировки учётных записей.

## Что прогнозирует Купман/DMD

1. Из агрегированной телеметрии L7 берётся вектор `x`.
2. Он нормируется относительно `t0`: `z = (x − x0) / s`.
3. На 64 небольших детерминированных отклонениях здорового режима строятся
   матрицы переходов. NumPy оценивает оператор:

   ```text
   K = C_cross · pinv(C_gram + 0.0001 · I)
   ```

4. Собственные значения ограничивают так, чтобы спектральный радиус `K` не был
   больше 0.995. Это предотвращает искусственное разрастание номинального
   прогноза.
5. На рабочем шаге используются только текущие и прошлые наблюдения: отклонение
   от `t0`, одношаговая невязка, 12-секундный тренд угроз и наблюдаемые
   предвестники. Расписание будущей атаки в расчёт не передаётся.

Прогноз строится максимум на 20 секунд. `forecast_risk_score` — инженерный балл
от 0 до 1, не вероятность атаки. Раннее предупреждение требует повторного
подтверждения тем же сенсором на двух последовательных шагах, распознанной цели,
типа наблюдаемого воздействия и превышения порога риска.

### А неизвестная атака?

Нет, оператор не умеет гарантированно назвать неизвестную атаку только потому,
что в ATT&CK есть похожая техника. Он может заметить **необъяснённое отклонение**
от нормы, если оно попало в измеряемые признаки. Без предвестника и без
подтверждения источника/цели программа честно оставляет состояние наблюдением,
а не обещает точный прогноз и не изолирует абонента.

## Как работает критерий Ляпунова

После получения оператора `K` программа решает дискретное уравнение:

```text
Kᵀ P K − P = −I
```

Для устойчивого `K` матрица `P` положительна и задаёт энергию отклонения:

```text
V = zᵀ P z / trace(P)
```

Решение выполняется удваивающей итерацией Смита. Это небольшой собственный код,
построенный из операций NumPy; он оставлен намеренно: в NumPy нет готового
решателя дискретного уравнения Ляпунова, а подключать тяжёлый SciPy только ради
одной функции увеличило бы зависимости проекта. На каждом расчёте экспортируется
Frobenius-невязка уравнения, поэтому качество решения проверяется.

Между шагами считается конечновременной темп роста энергии:

```text
dV/dt = ln((Vt + ε) / (Vt−1 + ε)) / (2 · Δt)
```

Положительное значение означает, что для текущей линейной модели отклонение
растёт; отрицательное — что оно затухает. Из положительного роста получается
`lyapunov_remap_pressure`. В `remap_pressure` берётся максимум обычных сигналов,
прогнозного давления и вклада Ляпунова, поэтому итоговое давление не меньше
вклада Ляпунова. План создаётся только при давлении выше 0.20 и подтверждённом
событии либо корректном раннем предупреждении.

Это строгое вычисление для применяемого линейного оператора `K`. Оно не является
доказательством глобальной устойчивости реальной нелинейной телеком-сети и не
является «показателем Ляпунова траектории»: для такого утверждения потребовался
бы отдельный расчёт вариационной системы.

## Матрицы тензоров, Кронекер и роль арбитра

Каждый `StateTensor` по-прежнему остаётся именованным одномерным вектором у
конкретного узла или связи. На каждом снимке `tensor_matrix.py` без потери
значений собирает для каждого уровня отдельную плотную матрицу:

\[
X_\ell \in \mathbb{R}^{n_\ell \times m_\ell},
\]

где строка — конкретная сущность уровня (узел либо связь), а столбец —
именованная метрика. В `snapshot-detail full` и `tensor` экспортируются оси и
все числа; `summary` оставляет оси, размер, хеш и норму, но матрица всё равно
строится в памяти и передаётся анализатору.

Чтобы не строить один оператор размера `(10 × 4)²`, полные матрицы сначала
преобразуются в четыре проверяемых признака отклонения от `t0` для каждого
уровня: среднее со знаком, RMS, максимум модуля и доля изменившихся значений.
Получается `Z ∈ R^(уровни × признаки)`. Структурированная ветка Купмана
использует

\[
\mathrm{vec}(Z_{t+1}) \approx (K_{level} \otimes K_{feature})\,\mathrm{vec}(Z_t),
\qquad
Z_{t+1}=K_{level} Z_t K_{feature}^{T}.
\]

`numpy.kron` применяется для точной проверки равенства двух записей на малом
состоянии. В рабочем расчёте хранится факторизованная форма `K_level` и
`K_feature`, а не их плотное произведение: само `kron` умножает размеры и не
устраняет проклятие размерности. Эта ветка даёт `tensor_matrix_koopman` как
дополнительную проверку согласованности матриц. Основной причинный прогноз
DMD и его телеметрические предохранители не заменяются синтетическим
«матричным риском».

КВУ (критически важный узел) — L2-устройство, ранжированное по
`gold_subscriber_count`: числу Gold-абонентов, для которых оно является точкой
доступа или лежит на безопасном пути к сервису. `K1` получают устройства с
максимальным счётчиком, затем следуют `K2–K4`. Это прозрачнее обычной степени
графа: много физических соседей ещё не означает большую цену потери для Gold.

Арбитр получает Хаусдорф, прогноз Купмана, производную функции Ляпунова,
остаток матричной ветки и критичность цели. Он строит конечную нормальную игру
«защитник—нарушитель»: действия защитника — `NO_REMAP`, наблюдение,
ремаппинг, изоляция подтверждённых источников с ремаппингом; действия нарушителя
— поддерживать, усиливать или распределять нагрузку. Если есть взаимные лучшие
ответы, экспортируется чистое равновесие Нэша. Если его нет, явно помечается
консервативный maximin-выбор — он **не** называется равновесием Нэша.

`sdn_controller.py` преобразует это решение в `sdn_intent`. Он используется
`remapping.py` только как описание внутреннего route overlay с правилом
Gold → Silver → Bronze и пределом 80%. `southbound_transport = none`: модуль
не открывает сокеты, не импортирует драйвер контроллера и не отправляет
OpenFlow-команды. OS-Ken подходит для отдельного авторизованного лабораторного
адаптера OpenFlow 1.3, но такой адаптер намеренно не включён в безопасный
симулятор без тестового контура и учётных данных.

ВВХ и ТТХ атак остаются параметрами ускоренного учебного сценария, а не
паспортом злоумышленника. Теперь каждая запись каталога и активного события
дополнительно содержит `target_device_context`: профиль фактической целевой
ёмкости, источник, подтверждённые и допущенные поля. Цель-абонент наследует
профиль своего RAN/OLT. Для C9500, NCS 5501 и R660 источники производителя
отделены от допущений; RAN и OLT всё ещё честно обозначены как scenario profile,
пока не выбран конкретный вендор и артикул для лаборатории.

## Используемые алгоритмы и библиотеки Python

| Задача | Библиотека или алгоритм | Где применяется |
|---|---|---|
| Граф сети | `networkx.Graph` | Топология L0–L8 и её атрибуты. |
| Маршрут данных | NetworkX Dijkstra по `latency_ms` в ограниченном data-plane view | В транзите разрешено только сетевое оборудование core, aggregation и явные узлы доступа RAN/OLT. Абонент, сервер и сервис не становятся промежуточными узлами. |
| Запасные пути | `networkx.shortest_simple_paths` | Ограниченный перебор кандидатов при remapping. |
| Центральность | `networkx.closeness_centrality` | Показатель близости маршрутизаторов ядра. |
| Хаусдорф | NumPy `linalg.norm`, `argmin/argmax`, блочное точное сравнение | Отклонение разреженного состояния от `t0` и отдельно изменение Gold-маршрутов. |
| Очередь L1 | Точные стационарные формулы birth–death для `M/M/1/128/∞/FIFO` | Вероятность блокировки, средняя длина и задержка абонентской очереди. |
| DMD/Купман | NumPy `pinv`, `eigvals`, матричное умножение | Регуляризованный оператор нормальной динамики, невязка и прогноз. |
| Факторизованный Кронекер | NumPy `kron`, `@`, нормы Фробениуса | Проверка точного плотного эквивалента и применение `K_level @ Z @ K_feature.T` без материализации большой матрицы. |
| Ляпунов | Удваивающая итерация Смита на NumPy-матрицах | Матрица `P`, энергия `V` и её темп роста. |
| Тренд | NumPy `diff`, `average`, `median`, `clip` | Робастный 12-секундный тренд наблюдаемых признаков угроз. |
| Случайность | `numpy.random.default_rng` и inverse-CDF Вейбулла | Воспроизводимые времена прихода событий в `predictive-demo`. |
| Визуализация | Matplotlib | PNG-графики, интерактивная карта и графическая диагностика. |
| Проверки | pytest | Структура `t0`, атаки, математика, ремаппинг и безопасность модели. |
| CLI и данные | стандартная библиотека `argparse`, `dataclasses`, `json`, `csv`, `pathlib`, `hashlib` | Параметры запуска, экспорт, валидация CSV и контроль происхождения файлов. |

## Границы модели

- Это не NMS, SOC или контроллер реального оборудования. `sdn_intent` —
  проверяемый план для внутреннего overlay, а не команда устройству.
- Данные об атаках и значения, явно помеченные `scenario_assumption`, не являются
  статистикой конкретного оператора.
- MITRE ATT&CK даёт таксономию, примеры процедур, источники телеметрии и меры
  защиты; он не заменяет измерения конкретной сети.
- Неизвестная атака без наблюдаемых признаков не может быть честно предсказана
  из одного `t0`.
- Для внешней телеметрии используйте отдельный порядок из
  [external_telemetry_validation_ru.md](external_telemetry_validation_ru.md).
